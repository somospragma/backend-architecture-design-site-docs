Un artefacto entra al hub con un pull request que agrega su ficha. Si la ficha no cumple el schema, el build falla y el PR no se puede fusionar.

## Criterios de entrada

- El repositorio es accesible para quien lo va a usar.
- El README explica la instalación y trae al menos un ejemplo.
- Tiene licencia. Si es de comunidad, una licencia open source.
- Tiene owners reales que responden por él.
- No tiene secretos ni datos de clientes.

<Aside type="caution" title="Trabajo hecho para un cliente">
	Algo creado para un cliente solo entra si Pragma tiene derecho a publicarlo.
</Aside>

## Pasos

<Steps>

1. Deja el README del artefacto como pide la guía de [cómo documentar un proyecto](../guides/documenting/).

2. Crea la ficha en `src/content/artifacts/<slug>.md` a partir de la plantilla [`templates/artifact.template.md`](https://github.com/somospragma/backend-architecture-design-site-docs/blob/main/templates/artifact.template.md).

3. Si eliges el modo `hosted`, agrega la documentación en `src/content/docs/artifacts/<slug>/` con la estructura de [`templates/docs-hosted/`](https://github.com/somospragma/backend-architecture-design-site-docs/tree/main/templates/docs-hosted).

4. Corre `pnpm build` en local para validar la ficha.

5. Abre el PR y completa el checklist de la plantilla.

</Steps>

## Cómo clasificar un artefacto

### Tipo: cómo se usa

El tipo es la navegación de arriba y no depende del lenguaje. Responde en orden y quédate con la primera respuesta que sea sí:

1. ¿Se agrega como dependencia? `library` (paquetes, SDKs, módulos de Terraform, charts).
2. ¿Se instala dentro de otra herramienta? `plugin` (Gradle, Maven, IDE, ESLint, Backstage).
3. ¿Se copia o se genera para empezar un proyecto? `template` (arquetipos, starters, scaffolds).
4. ¿Se ejecuta? `tool` (CLIs, apps de escritorio, servicios internos, bots).
5. ¿Corre en el pipeline de CI/CD? `automation` (GitHub Actions, workflows reutilizables, políticas).

Un plugin de Gradle que genera código es `plugin`, no `template`. Un CLI que crea proyectos desde un arquetipo es `tool`; el arquetipo es `template`.

### Disciplina: para qué trabajo sirve

Al menos una: `backend`, `frontend`, `mobile`, `data`, `ai`, `quality`, `integration`, `cloudops`, `devsecops` o `dx`. **La primera es la principal** y decide el grupo en la barra lateral.

### Lenguajes y tecnologías: filtros

- `languages` (al menos uno): en qué lenguaje lo usa quien lo consume. Una action de YAML es `yaml`; una librería de Spring es `java` o `kotlin`.
- `technologies` (opcional): frameworks, plataformas y herramientas de build, como `spring-webflux`, `nestjs`, `aws` o `gradle`.

Si falta un lenguaje o una tecnología (por ejemplo `ruby`), agrégalo en `src/content/taxonomy.mjs` en el mismo PR. La navegación no cambia.

## Estados

| Estado | Qué significa |
|---|---|
| `experimental` | Se puede probar, pero puede cambiar sin aviso. |
| `beta` | La API está casi cerrada y se aceptan reportes de errores. |
| `stable` | Listo para producción, con versionado semántico. |
| `deprecated` | No se recomienda. La ficha indica qué usar en su lugar. |

Los owners del artefacto proponen el estado y quienes aprueban fichas lo confirman en el PR.

## Retirar un artefacto

Primero se marca como `deprecated`, con un reemplazo o una nota que explique por qué. Después de un tiempo razonable, sus owners pueden pedir que se quite la ficha.
